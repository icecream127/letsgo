# letsgo 上下位机链路核查与对接清单

核查日期：2026-10-23。仅修改上位机；没有修改或烧录电控，没有给实物发送指令。
依据：桌面 new_way/CyberGear-1/CyberGear-1 最新源码，以及学长五份控制器与地图 2。
本文件描述开发核查版，不是已验证完赛的交付版本。旧 letsgo.tar.gz 未更新，不包含本轮修改。

## 一、动作完成反馈：有板内判断，没有在当前 UART8 帧中回传

完整证据链（以下电控相对路径以 CyberGear-1/CyberGear-1 为根）：

1. User/Motion/Action/action.cpp：ActionRunner::Start 设置 busy_；Update 按分段时间推进，在动作末尾置 busy_=false。LeaveHome 也按时间结束忙碌。
2. User/Motion/Action/action.h：IsBusy() 返回内部 busy_，GetAction() 返回当前动作。
3. User/APP/Control/app_motion.cpp：IsMotionBusy() 读取 ActionRunner::IsBusy()。
4. User/APP/Remote/app_remote.cpp：ProcessRemoteKey 在忙碌时丢弃动作键；UpdateRemoteStatus 只根据 IsStartupSelected、action_mode、SelectDiagnostic 组装状态，不读取 IsBusy/GetAction。
5. User/Remote/Uart/remote.cpp：Remote_SetStatus 缓存模式、故障、motor_id、detail；TIM7 经 UART8 发 RobotStatus_Encode 的 8 字节帧。
6. User/Remote/Uart/robot_status_protocol.h：帧为 A5 5A mode fault motor detail CRC8 0D，无动作编号、请求序号、busy、done 字段。
7. User/APP/Remote/app_diagnostics.cpp：detail 是故障详情，不是完成标志。零故障不等于动作完成。

电机 CAN 位置/速度反馈、板内初始化到位判断、串口 DMA/中断发送完成、动作执行结束，是不同概念。不能把其中一个当成上位机收到的动作完成 ACK。

不改电控时，上位机只能：导航用定位到点判断；一次性动作按代码时长加余量等待；持续监听故障；不把本地写成功当作执行成功。真实丢帧或忙时丢弃不能靠现有协议完全检测。不能安全地盲目重发跳跃。

## 二、双方已有协议，已逐项对照

| 项目 | 电控定义 | 上位机处理 |
|---|---|---|
| 物理串口 | UART8，115200，8N1，无硬件流控 | USB-TTL，默认 /dev/ttyUSB0；TX/RX 交叉、共地、电平匹配 |
| 下发格式 | 53 原始键值 45，3 字节，键值 1..23 | encode_key；不是文本 S2E，不带换行 |
| 模式键 | 9正常、10小坡、11桥B、12桥A、13大坡、14匍匐、15沙坑、16绕杆、17高墙、18台阶 | MODE_STATUS 与 COMMAND_MAP 对齐 |
| 基础动作 | 1左、2前、3右、4后、5站立，具体步态由模式决定 | 模式与动作组合校验 |
| 特殊动作 | 6/7/8/19/20 按模式映射；21趴下、22起身；23无对应动作 | 自动任务不发送21/22/23；不拿5当硬急停 |
| 回传格式 | A5 5A 模式 故障 电机 详情 CRC8 0D | 流式拆包、校验CRC、丢弃坏帧 |
| 模式确认 | 模式选择能回传，但不是Running/ready | 初始化仍需操作员确认 |
| 模式切换 | 只改 action_mode，不自动结束旧运动 | 新增先请求站立，再发模式，再等模式反馈；不能证明站立已执行 |
| 内部消息 | 电控不认识 ROS 消息 | /serial_send 四元素数组只在小电脑内部；拆成模式帧和动作帧 |

编译原有 Reset/FeedByte、Action_DecodeMode/Key、ActionRunner、状态编码函数进行主机测试：23 个合法键、错误文本/范围/帧尾及重同步、230 个模式与动作组合、10 个状态模式通过。理想 5ms 更新下10种一次性动作均在已配置保护时间以内。详见 firmware_protocol_result.json。
测试不编译整个 STM32 固件，不验证真实 CAN 延迟、实际姿态或机械成功。分段调度受实际循环周期影响，固定余量不是严格上界。

## 三、地图2与五个变体：不能仅取消注释

用户指定以现有地图2为准。本轮保持所有边界及 begin_x/begin_y 数值不变，运行副本集中于 lidar_ws/src/ros2_to_stm32/config/map_zones_config_2.json。

| 原控制器 | 航点总数 | 固定目标在全部调度区域外的数量 |
|---|---:|---:|
| task_to_do.py | 45 | 15 |
| task_to_do_mi.py | 43 | 14 |
| task_to_do_mi_2.py | 43 | 14 |
| task_to_do_unitree.py | 40 | 18 |
| task_to_do_unitree_2.py | 43 | 14 |

这是静态审计，不是完赛模拟；动态 x/y 航点未计入越界数量，区域外目标也可能是旧设计的交接意图，不能仅凭数量选版本。原 mi_2 与 unitree_2 完全相同，且使用未定义的“普通模式”。当前继续保留已适配 UART8 的 unitree 控制器，不切回旧串口代码。

具体阻断例子：
- 木桥A第8/9目标：(3.9,4.18)、(3.4,4.18)；地图2木桥B区域却在 Y=-4.9..-3.5。
- 木桥B首目标：(1.4,4.18)，仍在全部调度区域外。
- 大斜坡首目标：(1.2259,3.9718)，其区域在 Y=-4.9..-2.38。
- 绕杆多个目标超出其矩形，并且不属于任何其他调度区域。
- 木桥A/B有重叠；当前障碍优先、文件顺序首次匹配，A先于B。
- 地图2的 zon 展示/辅助数据仍含另一侧坐标，不能把它当作当前调度路线。
- 区域切换发生在位置跨界，而不是所有航点完成后；过早切换、反复跨界、末尾留在本区域都必须逐段验证。

所以：默认已选择 zones，不再默认两点demo；障碍分派是有效代码；普通区域 func_name=木桥A 作为进入木桥A控制器的入口。没有直接复活旧的阻塞sleep、无效模式名或同回调两个目标。
但是旧航点与既定地图2不构成已验证的完整路线。不可扩大区域掩盖问题，也不可擅自翻转参考点符号。下一步需逐段确定“该区域实际使用的全局目标、局部偏移、结束位置、切换区域和动作”，然后仅改上位机航点/调度。

## 四、本轮确定的上位机修复

- 统一UI、采点、控制器的地图2路径；参数集中在config，不依赖其他工作空间。
- 默认zones；恢复八障碍入口；普通区按配置选择处理器；区域外抛出暂停原因。
- 障碍采点要求有效A/B、新鲜里程计且暂停；运行时采点请求会暂停，需停稳后重新点击。
- 暂停时地图变化重新加载并清零进度；运行期间变化暂停；UI与控制器选区优先级一致。
- 修复沙坑、绕杆、高墙调试坐标被重复减原点。
- 修复UI“清零index”原来发无人订阅的话题，改用带结果的reset_route服务，运行/忙碌时拒绝清零。
- 固定每个航点首次进入时的动态x/y/yaw，避免目标跟随当前位姿漂移；增加总导航超时及无进展超时。
- 恢复一次性动作前非阻塞准备时间，默认1秒、沙坑退出3秒；不是阻塞ROS线程的sleep。
- 动作短写/写异常前先建立保护时间，结果未知时禁止立即重启并重复跳跃。
- 模式切换前发送站立请求；保留模式确认与一次性动作不自动重发。
- /motor_state 明确 busy_source=host_timer、action_completion_feedback=false，不伪装成电控反馈。

## 五、必须一起核对的剩余项（不要求修改电控）

| 优先级 | 项目 | 已知情况/验收方法 |
|---|---|---|
| 阻断 | 航点与地图2匹配 | 保留地图数值；逐障碍核对全局目标与区域交接，不用空场demo冒充完赛 |
| 阻断 | 动作选择 | 大斜坡目前沿用桥B模式11+6；第三台阶用9+6；需确认这是期望的实物动作，不按名字猜 |
| 高 | 实际部署版本 | Jetson安装路径和源码哈希应匹配；桌面改动不会自动同步Jetson；重新编译后检查导入路径 |
| 高 | 电控停止与上位机停止 | 5为站立；21忙时可能忽略；断线/小电脑掉电不保证停，独立急停必须可用 |
| 高 | 人工接管 | 同模式遥控键不体现在状态帧；上位机不能据此自动识别接管，先暂停再遥控 |
| 高 | 初始化完成 | 回传模式不等于Running；沿用遥控器初始化、人工确认、再踩点和arm |
| 高 | 动作完成 | 当前串口无done；本地计时不证明机械完成或命令已接受；单动作实测时长/效果 |
| 高 | 坐标方向 | A为原点，A到B为+X，转换Y为右侧；控制器再取负航向；验证左右转、前进、后退 |
| 高 | 雷达安装参考 | /Odometry是当前估计参考位姿；不自动等于足端或机身中心，踩点姿态及安装方向需一致 |
| 高 | 定位有效性 | 目前检查新鲜度和有限值，不等于检测FAST-LIO漂移/退化/跳变；须检查静止稳定、平移尺度、转向符号 |
| 中 | 航点容差/强制动作 | 5cm、角度容差、强制后退/转向需实测；超时参数不是修正错误路线的方法 |
| 中 | USB与网络 | 串口权限、设备稳定路径、TTL电平；雷达IP及网卡；禁止两个节点抢同一串口 |
| 中 | 地图显示和资源 | /Laser_map累计、PCD关闭；累计内存随时间增长，显示不是定位质量保证 |
| 中 | 请求与反馈语义 | last_tx仅本地写入；序号不上板；模式反馈无命令序号，存在人为并发切模式的不确定性 |
| 中 | 协议可靠性 | 下发只有帧头尾和范围检查，无CRC；不改电控不能单方面增强协议 |

## 六、开发版运行与审核约束

新增 /route_state 报告地图路径、hash、告警与ready。当前 reviewed_map_sha256 为空，arm会拒绝未审核路线。这是显式阻断，不是完整赛道已经修复，也不是用额外按钮替代路线修复。
该hash只绑定地图文件，不能证明航点源码已审核；修改控制器/电控后也必须清空并重新审核。不得只粘贴hash绕过已知越界问题。

只读检查，无运动：

```bash
bash run/check_route.sh --check
```

发现固定目标在全部区域外时退出码为2，这是已知路线问题，不是脚本崩溃。
已有环境可查看：ros2 topic echo /route_state；ros2 topic echo /motor_state。

离线回归（不打开实际串口）：

```bash
source /opt/ros/humble/setup.bash
export ROS_DOMAIN_ID=184 ROS_LOCALHOST_ONLY=1
cd lidar_ws/src/ros2_to_stm32
python3 -m pytest -q test/test_motor_adaptation.py test/test_motor_integration.py test/test_map2_chain.py
```

固件对照工具需要Python3、PyYAML、g++，传入电控源码根目录：
python3 validation/check_firmware_protocol.py /path/to/CyberGear-1
该工具只在临时目录编译测试程序，不改电控，不连接实物。

验收顺序：源码/安装路径一致 → 只收状态 → 初始化确认 → 定位与坐标检查 → 短距离基础动作 → 单个障碍 → 区域交接 → 全赛道。
当前尚未通过航点/地图一致性与实机阶段，不能直接执行完整赛道。
